# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Toolchain and commands

Use Bun 1.3.4. The repository is a single Bun package with a separate Rust/Tauri crate under `src-tauri/`.

```bash
# Install exactly from bun.lock
bun install --frozen-lockfile

# Web development (TanStack Start/Vite on port 3000)
bun run dev

# Full native desktop development (starts Tauri and its Vite servers)
bun run desktop:dev

# Static checks
bun run lint
bun run typecheck

# Production builds
bun run build                 # Web build
bun run build:desktop:ui      # Desktop React UI only
bun run desktop:build         # Native package for current host
bun run verify:release        # Typecheck + web build + desktop UI build

# Preview built web application
bun run preview
```

### Tests

The repository mixes Vitest and Node's built-in `node:test` runner, with no reliable aggregate command covering both. `bun run test` invokes Vitest, but default Vitest discovery may also match `.test.js` files authored for `node:test`; use the runner that matches the target file.

```bash
# Vitest
bun run test
bun run test:watch
bun run test:coverage

# One Vitest file or one named test
bun run test -- lib/calendar-date.test.ts
bun run test -- lib/calendar-date.test.ts -t "<test name>"

# One node:test file
node --test components/dashboard/preferences/dashboardPreferences.test.js

# Focused node:test scripts defined by package.json
bun run test:desktop-links
bun run test:assistant
bun run test:home-layout
```

Web CI runs locked installation, `bun run typecheck`, and the web production build; it does not run lint or tests. The desktop workflow also typechecks and builds the desktop UI, then creates native packages when manually dispatched or triggered by a matching desktop release tag. `bun run build` does not typecheck; run `bun run typecheck` separately or use `bun run verify:release` when both web and desktop UI builds matter.

## Architecture

### Web application

- React 18 and TypeScript are built with Vite 7 and TanStack Start/TanStack Router.
- File-based routes live in `src/routes/`. Route modules usually delegate rendering to `src/screens/`.
- `src/routes/__root.tsx` owns document metadata, global styles, `SessionProvider`, and the route outlet.
- `src/routeTree.gen.ts` is generated by TanStack Router. Never edit it manually.
- `start/router.ts`, `start/link.tsx`, and `start/dynamic.tsx` are compatibility wrappers used by current TanStack infrastructure; they are not Next.js runtime code.
- `/dashboard` is one application shell. Internal dashboard pages use URL hashes such as `#home` and `#settings/billing`, not nested TanStack routes.
- Dashboard section ids live in `components/dashboard/navigation/dashboardRegistry.ts`. The flashcards page is `#flashcards`; the former `#study` hash is kept only as an alias, and `LEGACY_SIDEBAR_ITEM_IDS` in `src/screens/dashboard.tsx` maps it for sidebar visibility/order preferences saved under the old id.
- `/dashboard?preview=1` renders the marketing preview used by the landing page iframes. Preview frames must never read or write user state: they skip saved themes (`loadAndApplySavedTheme`), skip stored animation settings, skip guided tours, and use the fixed `previewDashboardPreferences()` preset (simple Home). Use `isDashboardPreview()` from `lib/dashboard-preview.ts` when adding anything that touches browser storage.
- `src/screens/dashboard.tsx` is the main composition layer and is already large. Add domain behavior to hooks or focused components under `components/dashboard/<domain>/` rather than expanding this screen when possible.

### API and server boundaries

- API endpoints are TanStack file routes under `src/routes/api/`, implemented through `server.handlers`.
- Client code calls same-origin endpoints with `fetch`. Reusable Supabase, Stripe, portal-provider, scraping, and cryptographic domain logic belongs in `lib/`; small route-specific authentication or discriminator checks may remain beside their handlers.
- Mutating routes commonly combine signed-session authorization, same-origin/Fetch Metadata checks, bounded JSON parsing, and Supabase-backed rate limiting. Reuse existing helpers in `lib/csrf.ts`, `lib/rate-limit.ts`, and related server modules.
- Server code requires a Node-compatible runtime. Portal synchronization uses Node APIs, JSDOM, and optional Puppeteer.
- Google Calendar OAuth has not been ported to TanStack Start. Current calendar server routes return `501`; do not treat Calendar as an active server integration.

### Authentication and persistence

- Primary authentication is custom portal authentication, not Supabase Auth. Successful portal login creates or updates a Supabase user and issues a signed `millennium_session` cookie.
- `start/session.tsx` provides global session polling. `hooks/useDashboardData.ts` separately coordinates dashboard session state, cached portal data, durable snapshots, and refreshes. Authentication changes may affect both layers.
- Portal credentials and cookies are encrypted before persistence. Desktop browser handoff uses short-lived, single-use tokens with PKCE support.
- Authorization roles come from server-side `public.users.role`. UI gates are supplementary; API routes must enforce roles independently.
- Supabase is accessed through the server-side service-role client in `lib/supabase.ts`. Direct anonymous/authenticated table access is revoked by migrations.
- `supabase/migrations/` is authoritative ordered database history. Apply migrations in filename order before deploying dependent code. Do not improvise destructive down migrations against student data.
- Browser portal cache is owner-scoped local storage plus IndexedDB. Desktop cache is encrypted SQLite backed by an OS credential-store master key.

### Past papers

- The catalogue in `public.past_papers` is built server-side by `lib/past-papers/indexer.ts` and is read-only from every request path. Only the administrator-gated `/api/past-papers/reindex` writes it.
- Sources are registered in `public.past_paper_sources` and gated by their `enabled` flag. THSC ships disabled: its `robots.txt` disallows crawling (so the adapter reads the public `thsconline/s` GitHub repository instead), its documents sit behind a Google Apps Script the adapter never calls, and its licence needs an informal permission. Read `docs/past-papers-sources.md` before enabling a source or adding one.
- **The index never stores documents.** A paper is a pointer until a student saves or opens it. `PaperResource.accessMode` decides what happens then: `direct` may be fetched server-side, `referral` only ever links the student out. School trial papers are always referrals.
- `lib/past-papers/documents.ts` is the only outbound fetch of an index-supplied URL and is written as an SSRF problem: https-only host allowlist, no credentials, manual redirect following with every hop re-checked, PDF magic-number verification, and a streamed size cap. Do not relax any of those, and do not add a host to the allowlist that is not an official publisher.
- Difficulty is layered and carries its evidence: cohort attempts outrank a curated seed, which outranks structural heuristics. Structure alone never claims display confidence. Never emit a difficulty band without the rationale and sources that justify it — students plan around these labels.
- Timing authority runs document, then official course allowance, then nothing; `duration_source` records which, and the timer says so. Syllabus eras and course allowances apply to yr11/yr12 only — a junior assessment stamped with a three-hour HSC allowance starts the timer at roughly double.
- The exam timer is derived from an absolute deadline, never a decremented counter: background tabs are throttled, and a slow clock silently gifts a student extra time.

### Assistant trust and billing boundaries

- Treat model output and provider responses as untrusted input. Keep validation, size limits, timeouts, and provider guardrails centralized in `lib/assistant/guardrails.ts` and related server modules.
- Read-only assistant tools may execute directly. Dashboard mutations normally require short-lived, single-use approvals created and consumed server-side through the assistant approval layer. Narrow exception: `create_flashcard_sets` may execute during a valid server-reserved Study trial after server-side tool-sequence checks. Never create general approval bypasses or execute model-proposed mutations from client state alone.
- Model entitlement, usage budgets, and usage recording remain server-side in billing/assistant routes. Do not rely on client-selected models or client-reported usage for authorization or cost control.

### State and feature organization

- There is no Redux-style global store. State primarily lives in React components and domain hooks.
- `hooks/useDashboardData.ts` is the central portal/session data coordinator: it checks identity, hydrates owner-scoped cache, loads the server snapshot, synchronizes stale portal data, and persists successful snapshots.
- Preferences and notifications use server persistence with account-scoped local fallback for offline operation.
- Dismiss-once notices and prompts are registered in `lib/one-time-notices.ts`. Add new one-time UI there so the administrator debug panel can re-arm it; do not invent ad-hoc `localStorage` flags.
- Guided tours live in `lib/tour/dashboardRegistry.ts` (steps, ids, release cutoff) with the runtime in `components/tour/`. A step whose target only exists after some UI opens should set `action.auto` so the guide performs the click on entry instead of rendering a redundant preview button. Account creation date versus `TOUR_RELEASE_CUTOFF` decides the welcome/full tour against the shorter update tour.
- Shared UI primitives live in `components/ui/`. Dashboard feature components live under `components/dashboard/<domain>/`. Shared hooks and server/domain utilities remain in root `hooks/` and `lib/`.
- `@` is the repository-root runtime alias. Root directories use imports such as `@/components/...` and `@/lib/...`; files under `src/` use `@/src/...` rather than `@/screens/...`.

### UI system

- Styling combines Tailwind CSS v4, shadcn `base-nova`, Base UI primitives, CVA variants, CSS variables, and legacy CSS modules.
- `styles/globals.css` is the token authority and also contains compatibility variables for the legacy dashboard CSS.
- Runtime theme application lives in `lib/theme.ts` and updates both `--app-*` compatibility variables and shadcn semantic variables such as `--background`, `--primary`, and `--border`. Keep both token layers synchronized when changing themes.
- Compose existing shadcn components from `components/ui/` for UI changes instead of introducing native browser/OS UI structures. Newer dashboard pages (Classes, Classroom, Flashcards) use shadcn primitives and semantic tokens directly rather than adding to `styles/Dashboard.module.css`.
- PDF surfaces (reports and past papers) share `components/pdf/`. The viewer keeps two scales: `liveScale` drives layout immediately, `rasterScale` trails it until a zoom gesture settles. Do not collapse them — rasterising per wheel notch queues overlapping `page.render()` calls against one canvas, which pdf.js aborts, leaving pages torn and apparently cropped. Always cancel the in-flight `RenderTask` before starting another, and anchor zoom against painted geometry rather than the requested scale.
- Dashboard scroll containers (`DashboardPageBody`, `.contentWrapper`) scroll on both axes. Do not narrow them back to `overflow-y`: browser zoom pushes card grids wider than the frame and a clipped horizontal axis makes that content unreachable.
- Home is one ordered card list (`HomeLayout.items`); a card owns a column through `itemColumns` and a width through `itemSpans`, set from its right-click menu. There are no pixel card positions and no separate advanced/free-canvas mode — do not reintroduce absolute card coordinates, which broke at every page width. Freeform ink, text and lines (`canvasElements`) sit on an absolute layer over that grid.
- Card placement is computed in `components/dashboard/home/homePlacement.ts` and written onto each card as an explicit `grid-column`/`grid-row`; `items` order only decides how cards stack *within* a column. Do not hand Home back to CSS auto-placement (and never `grid-auto-flow: dense`): auto-placement derives a card's column from the height of everything before it, so a card that merely grew threw unrelated cards into the other column. Column changes only in `handleHomeDragMove`, from the pointer's own x position.
- `homeColumnCount` is measured back off the laid-out grid rather than taken from the column preference, because a responsive override can collapse Home to one column. Feed the preference to `data-columns` and the measurement to placement — swapping them latches Home at one column.
- Home card dragging uses one dnd-kit `SortableContext` plus a `DragOverlay`; the source card stays as a dimmed placeholder. Keep the overlay: without it the dragged card snaps back to its slot until release. The sorting strategy deliberately returns no transform — a rect-rotating strategy assumes uniform slots and throws cards across a masonry grid.

### Desktop application

- `desktop/` contains the desktop React entry/router and reuses web screens.
- `src-tauri/` is the Tauri 2 Rust host. It owns secure local storage, native Classroom synchronization, deep links, updates, and local asset/API serving.
- Desktop development uses UI port `14200`, local web/API port `14201`, and proxies `/api/*` from the UI to the server. Use `bun run desktop:dev` for the complete native application; `bun run dev:desktop` only starts the two development servers.
- Packaged builds serve UI assets from loopback ports `3001` through `3010`. API proxy origin is selected at compile time by `MILLENNIUM_DESKTOP_BACKEND_ORIGIN`; without it, builds default to `http://millennium-five.vercel.app`. Setting this variable after packaging has no effect. Preserve loopback, Host/Origin, redirect, and body-size protections in `src-tauri/src/local_server.rs`; see `docs/desktop-release.md` before release builds.
- `src-tauri/src/live_shell.rs` keeps installed desktop copies on the deployed UI. `bun run build:web` publishes the desktop bundle to `public/desktop-shell/` (generated, gitignored) with a `shell.json` manifest; the native host downloads it, verifies every file digest, and activates atomically, falling back to the embedded bundle on any failure. Raise `desktopShell.minimumNativeVersion` in `package.json` whenever new UI depends on a new Tauri command, otherwise older installations will load a shell their host cannot serve.
- Desktop commands must be listed in three places to work: `tauri::generate_handler!` in `src-tauri/src/main.rs`, `COMMANDS` in `build.rs`, and `src-tauri/capabilities/default.json`. Omitting the last two fails the build or rejects the call at runtime.
- Desktop UI builds output to `dist/desktop` and deliberately remove copied `/downloads/` installers to prevent recursive packaging.
- Changes intended for installed desktop applications require matching version bumps in `package.json` and `src-tauri/Cargo.toml`, followed by a matching `desktop-v<version>` tag for release builds.
- Classroom sync is gated by real operating-system consent, not only the in-app dialog. `continue_classroom_sync` re-checks `browser_permission_status` and refuses with `BROWSER_PERMISSION_REQUIRED` unless `ClassroomBrowserPermission::allows_reading()`. The macOS Automation prompt depends on `NSAppleEventsUsageDescription` in `src-tauri/Info.plist`, which Tauri merges into the packaged bundle only — unpackaged dev runs will not prompt.

## Repository-specific constraints

- Use fixtures or an approved synthetic account for portal development and smoke checks. Do not use real student accounts or production credentials.
- Direct HTTP portal sync is the default. Chromium fallback is explicit opt-in and must remain disabled without provider-policy and operational review. Do not add CAPTCHA, bot-detection, or access-control evasion.
- Keep `PUPPETEER_DISABLE_SANDBOX=false` unless equivalent process isolation has been formally reviewed.
- Keep generated Vite bundles under `_app-assets`. Changing this to `assets` collides with `public/Assets/` on case-insensitive macOS filesystems and breaks chunks/CSS.
- `public/downloads/desktop/` contains published installer artifacts, not normal frontend source.
- `dist/`, `node_modules/`, `src-tauri/target/`, `src-tauri/gen/`, and `.tanstack/` are generated or tool-managed output.
- Administrator status must come from `public.users.role`, never cookies, request bodies, or user-editable metadata. Self-demotion and removal of the final administrator are intentionally blocked.
- The administrator "Debug events" panel only re-arms the acting administrator's own one-time notices (local storage plus their own tour preferences). Keep it that way: it is a self-scoped debug affordance, not a way to change another account's client state.
- Keep server secrets and service-role/provider keys out of `VITE_*` variables and client bundles. `lib/server-environment.ts` validates core server settings; assistant-provider and Stripe settings are feature-specific and may be validated only when those features execute.
- Use `docs/production-release-runbook.md`, `docs/desktop-release.md`, and `docs/administrator-tools.md` as authoritative operational references rather than duplicating release procedures here.
